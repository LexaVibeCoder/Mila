# Глобальный журнал действий

**Файл:** `core/action_journal.py`

Журнал отвечает на вопрос «что я делала сегодня?» и склеивает чаты в одну
временную ось. Он хранится в `mila.db` и попадает в system prompt отдельным
блоком между состоянием/потребностями и дневником.

## Место в контексте

```
[system prompt: персона + header]
[контекст отношений]
[где ты + поведение состояния]
[твоё состояние: fatigue / boredom / social need]
[что ты делала сегодня]        ← глобальный журнал
[дневник]
[саммари и/или история текущего чата]
[свежее событие]               ← последнее действие этого хода
```

Журнал читается **один раз в начале хода** (`ThinkPipeline._run_stream`).
События, созданные во время хода, добавляются в конец контекста как
`[событие] ...` и попадают в блок журнала только на следующем ходе. Поэтому
одно и то же событие не дублируется в system prompt и в конце хода.

## Что попадает в журнал

| Действие | Пишется? | Как |
|----------|----------|-----|
| `enter_dialog` | да | вход в чат: время, алиас/имя, прошлое состояние, длительность прошлого состояния, `note` |
| `enter_rest` | да | время, `note` |
| `enter_working` | да | время, `note` |
| `start_sleep` | да | время, планируемая длительность, `note` |
| пробуждение | да | время, реальная длительность сна |
| `send_message` | да | время, чат, текст до 200 символов |
| `search_memory` | нет | результат нужен только текущему ответу |
| `write_diary` / `update_diary` | нет | сам дневник и есть запись |
| `peek_recent_chats` | нет | чтение чужих чатов, а не действие |
| обычные ответы в диалоге | нет | остаются репликами ассистента в контексте чата |
| входящие уведомления | нет | уже видны в истории переписки |

Переходы состояния пишутся из **всех источников**: тулы модели, auto-rest по
тишине, auto-sleep, ручной запуск из Observatory и crash recovery. Так журнал
не врёт, если состояние сменилось не по инициативе модели.

## Схема `action_journal` (`mila.db`)

Таблица создаётся лениво (`_ensure_table()`), идемпотентно:

```sql
CREATE TABLE action_journal (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,          -- UTC ISO
    kind TEXT NOT NULL,                -- state | wake | send_message
    state TEXT,                        -- rest | dialog | working | sleep
    prev_state TEXT,
    chat_id TEXT,
    chat_name TEXT,
    chat_alias TEXT,
    prev_chat_id TEXT,
    prev_chat_name TEXT,
    prev_chat_alias TEXT,
    prev_duration_seconds REAL,
    note TEXT DEFAULT '',
    text TEXT DEFAULT '',
    meta TEXT DEFAULT ''               -- JSON: source, duration_minutes, duration_seconds
);
```

`chat_name`/`chat_alias` — снимок на момент события. Если чат переименуют,
журнал продолжает показывать понятное старое имя, а не голый ID.

## Длительности

Длительность состояния считается автоматически при выходе из него:
`prev_duration_seconds = now - presence_state.updated_at`. При обновлении
`note` в том же состоянии/чате `updated_at` не сбрасывается, поэтому
«до этого была в rest 21 мин» остаётся правдой.

Для отображения диалог схлопывается в интервал:

```
[18:37–18:58] была в чате иван
[18:58] перешла в rest
```

Открытый диалог показывается как `[19:14–сейчас] в чате sokol`. Остальные
переходы (`rest`/`working`/сон) — отдельными строками.

## Окно показа

По умолчанию: **с локальной полуночи до сейчас** плюс хвост сна или открытого
диалога, начавшегося вчера. Это покрывает сон через полночь:

```
[вчера 23:30] легла спать на 7 ч
[06:40] проснулась, спала 7 ч 10 мин
```

События до местной полуночи помечаются `вчера`, чтобы не путать хвост сна
с сегодняшним временем.

Отображение ограничено `JOURNAL_MAX_LINES = 60` строк; старые строки
отбрасываются только из промпта, в БД остаются.

## Свежее событие

`presence._set()` возвращает `journal_event` — полную строку события. Executor
передаёт её в результате действия, а пайплайн добавляет в конец контекста:

```
Presence switched. Decide in the new state now.
[событие] [2026-11-06 19:14:30] ты зашла в чат sokol (Федос) из rest, до этого была в rest 21 мин. заметка: ...
```

`send_message` журналируется в `deliver_messages()` **после фактической
отправки** (а не когда тул вернул `ready`), поэтому отменённая отправка не
оставляет ложного следа.

## Сон

`start_sleep()` сам переключает presence и пишет старт один раз — с реальным
предыдущим состоянием и планируемой длительностью. Пробуждение пишется в
`commit_all()` / `rollback_all()` / recovery по `sleep_state.started_at`, поэтому
длительность реальная, а не заявленная. `_presence_to_rest()` при пробуждении
вызывается с `journal=False`, чтобы не добавлять вторую строку «перешла в rest».
