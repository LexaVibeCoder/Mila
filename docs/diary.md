# Дневник

SQLite (`diary_entries` в `context_buffer.db`) хранит текст, категорию и время
создания и изменения в UTC. Схема создаётся и обновляется при старте бота
и Observatory. Записи, которые уже обработал сон, отмечаются в SQLite как
архивные. Они нужны для отчёта и проверки точных повторов. В контекст модели
и повторный ночной анализ они не попадают. Номера новых записей продолжают сквозную
нумерацию после ночного архивирования.

## Запись и редактирование

`write_diary` сразу сохраняет запись. Проверка выполняется локально и
пропускает точные повторы среди активных записей и истории за текущий
локальный день. `update_diary` сохраняет полный текст по ID активной
записи и отклоняет точный дубль другой отдельной записи. Максимальная длина записи —
1200 символов. Число записей за день не ограничено.

- `day_entries` — события и наблюдения.
- `reflection_entries` — мысли и чувства.

## Реорганизация

Бот проверяет новые и вручную отредактированные записи раз в час. Перед
ночным анализом дневника запускается ещё один проход. Если новых версий
нет, запроса к LLM нет. Разбор ограничен четырьмя пакетами и 45 секундами
за проход. Записи из разных категорий и локальных дней рассматриваются
отдельно. Модель получает только заметки из текущего пакета, включая
несколько уже проверенных для сравнения. Модель указывается в
`DIARY_LLM_MODEL`. При пустом значении используется настроенная ночная
LLM в отдельном запросе без истории чата.

Модель предлагает объединить конкретные ID и формулирует итоговый текст.
Код проверяет формат и длину, что ID принадлежат пакету и что хотя бы одна
запись в группе ещё ждала разбора. Если запись изменилась после чтения,
пакет откладывается. Объединение сохраняет ID самой ранней записи группы.
Исходные записи остаются в SQLite. Объединённые строки помечаются
`merged_into`, а предыдущий текст основной строки и ID источников сохраняются
в `diary_reorganization_history`. При сбое API или некорректном плане
записи остаются доступны и ждут следующего прохода.

## Отчёт и контекст

`get_all_diary_entries(category=None, local_day=None)` возвращает активные
записи по времени создания. `get_today_diary_context()` берёт только записи
текущего дня и включает ID для редактирования. Границы дня и отображение
времени учитывают `LOCAL_TIMEZONE`, при пустой настройке используется зона ОС.

Отчёт `data/daily reports/ДД.ММ.ГГГГ.md` показывает отдельные и объединённые
записи за этот день по порядку создания. Исходные версии остаются в SQLite. В заголовке каждой записи есть категория,
локальное время и ID. Изменение старой записи обновляет отчёт за день её
создания. Инструмент сообщает результат экспорта в `daily_file_synced`.
Если файл записать не удалось, изменения остаются в SQLite. Повтор операции
обновляет файл с тем же ID. Экспорт после фонового объединения при сбое
повторяется в следующем проходе.

Observatory читает отчёты через `GET /api/diary`, `GET /api/diary/today` и
`GET /api/diary/{date}`. Список отсортирован по дате от новых к старым.
`/today` возвращает текущую локальную дату в формате `ДД.ММ.ГГГГ`.

## Ночной цикл и резервные копии

`clear_diary()` сохраняет копию активных записей в
`LOG_DIR/diary_logs/diary_ГГГГММДД_<uuid>.md` перед архивированием. Дата в
имени локальная. Относительные `LOG_DIR` и `DAILY_REPORTS` считаются от корня
проекта.

Ночной commit пишет активные записи в staging до архивирования и передаёт
тот же снимок в `clear_diary`. Если бэкап не записался или активные записи
изменились во время сохранения, commit завершается ошибкой. При сбое после
архивирования recovery возвращает записи из staging в активный дневник.
