# Дневник

SQLite (`diary_entries` в `context_buffer.db`) хранит текст, категорию и время
создания и изменения в UTC. Схема создаётся и обновляется при старте бота
и Observatory. Записи, которые уже обработал сон, отмечаются в SQLite как
архивные. Они нужны для отчёта и дневного лимита, в контекст модели и повторный
ночной анализ они не попадают. Номера новых записей продолжают сквозную
нумерацию после ночного архивирования.

## Запись и редактирование

`write_diary` проверяет точные повторы среди активных записей и архива за
текущий локальный день. Точный повтор пропускается. `update_diary` принимает
полный текст новой версии и отклоняет текст, совпадающий с другой записью.
Лимиты — 1200 символов на запись и три записи каждой категории за локальный
день. При смене категории лимит проверяется для дня создания записи.
При достижении лимита инструмент сообщает об этом. Подсказка обновить
существующую запись появляется при смысловом совпадении с конкретной записью.

- `day_entries` — события и наблюдения.
- `reflection_entries` — мысли и чувства.

Основная модель вычитывает грамматику перед сохранением. Если настроена
decision-модель, она также оценивает вероятность явной грамматической ошибки.
При оценке от 0,80 основная модель получает подсказку перечитать текст и при
необходимости исправить его через `update_diary`.

### Decision-модель

Заполните `DECISION_API_KEY` и `DECISION_MODEL` в `.env`. Для OpenRouter
укажите полный ID decision-модели и `DECISION_API_BASE=https://openrouter.ai/api/alpha`
или используйте базовый URL по умолчанию. Клиент отправляет запрос на
`https://openrouter.ai/api/alpha/decisions` с отдельным ключом.
Для обеих категорий проверка отправляет провайдеру черновик и до шести
последних активных записей нужной категории. При явном редактировании
передаётся и целевая запись. Точное совпадение определяется локально,
до вызова API. Грамматика, смысловое совпадение и ID проверяются в одном
запросе на вызов инструмента.

- Смысловой повтор с оценкой от 0,65 пропускается.
- Если черновик существенно дополняет существующую запись и сам сохраняет
  её важные сведения, при оценке от 0,85 `write_diary` обновляет запись
  по прежнему ID. Экспорт обновляется за день создания записи.
- Если дополнение нужно объединить со старым текстом или оценка полной
  замены от 0,65 до 0,85, основная модель получает ID и старый текст. Она
  составляет полную версию и передаёт её отдельным вызовом `update_diary`.
- При явном `update_diary` проверка с порогом 0,65 пропускает
  перефразирование целевой записи без существенных изменений и смысловой
  дубль другой записи. Явные исправления текста и смена категории допустимы.

Если совпадение неясно, модель недоступна или отсутствуют настройки,
действуют локальные проверки. Если выбранная запись изменилась или попала
в архив во время проверки, результат отклоняется. Перед сохранением записи
без совпадения также проверяется, что список кандидатов остался актуальным.

Тест `tests/test_diary_benchmark.py` сравнивает модель и ближайший эмбеддинг
`openai/text-embedding-3-small` по косинусному сходству с порогом 0,85.
Он использует размеченные синтетические примеры на русском и печатает число
пропущенных дублей и ошибочно отсеянных новых записей. Для запуска передайте
в окружение `DECISION_API_KEY` и `DECISION_MODEL` для OpenRouter. Если задан
`DECISION_API_BASE`, он должен указывать на OpenRouter. Задайте
`MILA_RUN_DIARY_BENCHMARK=1`. Запуск из каталога вне репозитория с
`PYTHON_DOTENV_DISABLED=1` позволяет использовать только переменные окружения.

```bash
PYTHON_DOTENV_DISABLED=1 MILA_RUN_DIARY_BENCHMARK=1 \
  /path/to/Mila/.venv/bin/python -m pytest -m integration -s \
  /path/to/Mila/tests/test_diary_benchmark.py
```

## Отчёт и контекст

`get_all_diary_entries(category=None, local_day=None)` возвращает активные
записи по времени создания. `get_today_diary_context()` берёт только записи
текущего дня и включает ID для редактирования. Границы дня и отображение
времени учитывают `LOCAL_TIMEZONE`, при пустой настройке используется зона ОС.

Отчёт `data/daily reports/ДД.ММ.ГГГГ.md` показывает все сохранённые записи
за этот день по порядку создания. В заголовке каждой записи есть категория,
локальное время и ID. Изменение старой записи обновляет отчёт за день её
создания. Инструмент сообщает результат экспорта в `daily_file_synced`.
Если файл записать не удалось, изменения остаются в SQLite. Повтор операции
обновляет файл с тем же ID.

Observatory читает отчёты через `GET /api/diary`, `GET /api/diary/today` и
`GET /api/diary/{date}`. Список отсортирован по дате от новых к старым.
`/today` возвращает текущую локальную дату в формате `ДД.ММ.ГГГГ`.

## Ночной цикл и резервные копии

`clear_diary()` сохраняет копию активных записей в
`LOG_DIR/diary_logs/diary_ГГГГММДД_<uuid>.md` перед архивированием. Дата в
имени локальная. Относительные `LOG_DIR` и `DAILY_REPORTS` считаются от корня
проекта.

Ночной commit пишет активные записи в staging до архивирования и передаёт
тот же снимок в `clear_diary`. Если бэкап не записался или активные записи
изменились во время сохранения, commit завершается ошибкой. При сбое после
архивирования recovery возвращает записи из staging в активный дневник.
