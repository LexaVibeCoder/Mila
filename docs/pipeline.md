# Основной пайплайн (ThinkPipeline)

**Файл:** `core/pipeline.py`

`ThinkPipeline` — ядро рассуждения Милы. Это **direct-tools** цикл: LLM получает
реальные функции (`enter_dialog`, `send_message`, `search_memory`, ...), а не
обёртку `think()`. В диалоге ответ приходит обычным текстом: пузыри разделяются
пустой строкой, пустой ответ означает молчание.

Название `ThinkPipeline` сохранено для совместимости; алиас — `MilaPipeline`.

## Логика работы

```
process_message_stream() / process_message()
    │
    ├── req_user / req_chat — снимок хода (параллельные чаты не перетирают self.*)
    ├── journal_context = get_journal_context()   — снимок журнала на весь ход
    ├── messages = list(agent_internal_history)
    │   ├── proactive_block? → system-блок с инструкциями и списком чатов
    │   └── иначе → notification-блок для rest/working или чужого чата (последние 2000 символов)
    ├── _attach_media(): текущие фото/аудио + последние 3 фото и 2 аудио из истории
    │
    ├── while iteration < max_iterations (runtime, по умолчанию 7):
    │   ├── presence = снимок TurnContext / get_presence() (обновляется только этим ходом)
    │   ├── system_prompt = build_main_llm_system_prompt(
    │   │       ..., journal_context=journal_context)          (заново каждый раз)
    │   ├── tools = get_tool_definitions(presence_state, include_proactive=...)
    │   ├── LLM.generate(messages, system_prompt, tools, tool_choice="auto")
    │   │
    │   ├── нет tool_calls:
    │   │   ├── dialog → split_reply_bubbles(content)
    │   │   │   ├── пусто → silence
    │   │   │   └── абзацы через пустую строку → reply
    │   │   └── rest/working:
    │   │       ├── пусто → silence
    │   │       └── текст → нарушение протокола → reminder + ретрай
    │   │
    │   └── есть tool_calls:
    │       ├── контент этого хода НЕ отправляется (это рассуждение)
    │       ├── некорректные JSON-аргументы → ошибка в контексте модели
    │       ├── одинаковые имя и аргументы → только первое выполнение за ход
    │       ├── для каждого action: execute_action → apply_action_effect
    │       ├── start_sleep(sleeping) → silence (старт журналируется в sleep manager)
    │       ├── enter_*/switched → system-сообщение с `[событие]` в конце → повтор
    │       ├── send_message(ready) → кандидат на финальный ответ (журнал — после отправки)
    │       ├── search_memory → инъекция результатов/ошибки → повтор
    │       ├── peek_recent_chats → инъекция чатов → повтор
    │       ├── write/update_diary → инъекция результата → повтор
    │       └── иначе → reminder и следующий круг
    │
    └── исчерпание max_iterations без решения → error с кодом iteration_limit
```

## Состояния и протокол

Поведение зависит от `presence.state`:

| Состояние | Ответ | Инструменты |
|-----------|-------|-------------|
| `rest` | текст без инструмента вызывает напоминание и повтор в рамках лимита | `enter_dialog`, `send_message` (одна отмашка), `enter_working`, `start_sleep` |
| `working` | то же | `enter_dialog`, `send_message`, `enter_rest`, `start_sleep` |
| `dialog` | обычный текст в текущий чат; пустой ответ = молчание | `send_message` (разовая отмашка), `search_memory`, `write_diary`, `update_diary`, presence-тулы, `start_sleep` |
| `sleep` | пайплайн обычно не работает | `enter_dialog`, `start_sleep` |
| proactive | `rest/working` + `peek_recent_chats` | те же + peek |

После `enter_dialog` пайплайн **пересобирает system prompt и tools** и вызывает
LLM снова — уже по правилам диалога. После `enter_rest`/`enter_working` — наоборот.
Причина `note` обязательна и явно включается в сообщение о переходе даже при
ошибке журнала. В контекст добавляются история и профиль выбранного чата; чужая
история не переносится, кроме указанной самой моделью причины перехода. Если
уведомление пришло не из фокусного чата, его текст помечается отдельно.
Список всех известных чатов с алиасами доступен модели в system prompt.
В уведомлении и блоке presence LLM видит постоянный алиас чата вместо ID;
executor разрешает алиас в ID до изменения presence или отправки. Неверный
алиас возвращается в контекст как ошибка и не приводит к отправке.

При смене состояния пайплайн добавляет в **самый конец** контекста свежее
событие журнала:

```
Presence switched. Decide in the new state now.
[событие] [2026-11-06 19:14:30] ты зашла в чат sokol (Федос) из rest, до этого была в rest 21 мин. заметка: ...
```

`journal_context` читается один раз в начале хода, поэтому это событие не
дублируется в system prompt. На следующем ходе оно уже находится в блоке
«Что ты делала сегодня». `send_message` пишется в журнал в
`core.delivery.deliver_messages()` после успешной отправки. `search_memory`,
`peek_recent_chats` и дневник в журнал не попадают. Подробности —
[action-journal.md](action-journal.md).

## Формат ответа в диалоге

Ответ — обычный текст. Пузыри разделяются пустой строкой (`\n\n`, пробелы
между переводами строк допускаются):

```
первый пузырь

второй пузырь
```

- `split_reply_bubbles()` режет ответ по пустым строкам, лимита на число
  пузырей нет;
- границей пузыря также считается `\n` перед строкой, начинающейся с
  `[YYYY-MM-DD HH:MM(:SS)]`: модель иногда помечает желаемый разрыв
  собственным timestamp вместо пустой строки;
- одиночный `\n` внутри абзаца сохраняется как есть;
- пустой ответ или ответ из пробельных символов без вызовов инструментов
  сразу завершает ход молчанием в `dialog`, `rest` и `working`;
- `[YYYY-MM-DD HH:MM(:SS)]` в начале пузыря (в т.ч. скопированный из
  истории) удаляется; timestamp в середине строки не трогается;
- `response_format` больше не запрашивается: провайдер получает обычный
  текстовый ответ.

## Стриминговые события

`process_message_stream()` — асинхронный генератор (его потребляет `core/queue.py`
и `core/proactive.py`):

```
thought       → {"type": "thought", "thoughts": "..."}
action        → {"type": "action", "action": {...}}
search_result → {"type": "search_result", "content": "..."}   (memory или peek)
reply         → {"type": "reply", "texts": [...], "text": "...", "via": "bubbles"|"send_message_brush_off"}
silence       → {"type": "silence", "reason": "..."}
done          → {"type": "done", "result": {...}}
error         → {"type": "error", "error": "...", "result": {...}}
```

Событие `reply` **не содержит получателя**: `TurnContext` хранит снимок
глобального фокуса для обычного текста или явно разрешённую цель записки.
`_run_stream`/`process_message_stream` принимают `turn=TurnContext(...)`;
внутри `presence` снимается на старте и обновляется после собственных переходов;
перед отправкой проверяется, что внешнее изменение не сделало снимок устаревшим.

`process_message()` выполняет тот же цикл и возвращает `result` целиком.
`result["reply_chat_id"]` остаётся для логов/Observatory и вычисляется из
`turn.resolve_target()`, а не из события.

## Ошибки

При HTTP 401/403 LLM-клиент сразу завершает запрос и пишет событие уровня
ERROR с HTTP-статусом. Повторы HTTP 429, 5xx, таймаутов и ошибок соединения
выполняются в рамках бюджета LLM-клиента с задержкой. Если провайдер вернул
числовой `Retry-After`, он используется для расчёта задержки. В диагностику
попадает безопасное описание сбоя без тела ответа провайдера.

Исчерпание лимита итераций считается ошибкой хода. Намеренное молчание и
переход в сон завершают ход успешно. При ошибке структура результата
сохраняется, включая уже выполненные действия, завершённые ответы модели,
системный промпт первой итерации, изменения контекста и число начатых LLM-итераций. Код ошибки различает
`iteration_limit`, `llm_authorization`, `llm_request` и `pipeline_error`.

В живых входящих и проактивных ходах диагностика доступна на странице
Pipeline в Observatory. Очередь и проактивный планировщик также отправляют
текст ошибки в «Избранное» Telegram-аккаунта Милы. Уведомление адресуется
этому аккаунту по ID из `getMe()` и проходит вне маршрута диалога. Если
Telegram недоступен или текст превышает лимит уведомления, полная
диагностика остаётся в журнале. В тестовом чате ошибка отображается в
истории сессии.

## Медиа

`_attach_media()`:

- текущий батч (фото/аудио) вставляется в **последнее** user-сообщение;
- последние `MAX_HISTORY_IMAGES = 3` фото и `MAX_HISTORY_AUDIOS = 2` аудио
  подтягиваются из `chunks.media_path` и вставляются **в свои** сообщения по
  плейсхолдерам `[фото...]` / `[голосовое...]`;
- если сообщение уже вышло из контекста — байты отбрасываются, а не
  приклеиваются к текущему ходу;
- аудио конвертируется в wav/16kHz mono через ffmpeg; при отсутствии ffmpeg
  нативный звук пропускается (плейсхолдер остаётся);
- при HTTP 400, 415 или 422 в запросе с аудио `LLMClient` может сделать один
  текстовый повтор в рамках бюджета.

## Sandbox (Observatory Test Chat)

`process_message(..., sandbox=True, sandbox_context=..., sandbox_diary_context=...)`
и потоковый вариант:

- presence берётся из `TurnContext`-снимка сессии (`dialog` / `rest` /
  `working`); глобальный `presence_state` не читается и не меняется;
- определения тулов **не фильтруются** — Мила видит обычный набор для своего
  состояния. `ToolExecutor` с `sandbox_context` пишет `write_diary` /
  `update_diary` в дневник сессии, переключает состояние сессии через
  `enter_*`, а `send_message` в чат сессии отдаёт как реплику;
- `start_sleep`, `peek_recent_chats`, `send_message` в чужие чаты и неизвестные
  действия возвращают `status="ignored"` без сообщения модели;
- блок реального дневника заменяется `sandbox_diary_context`; в чат-листе
  остаётся только чат сессии; никакого «тестового» текста в промпт не
  добавляется;
- эффекты State Agent (`apply_action_effect`) не применяются;
- `logs/pipeline_*.json` не создаётся.

## Логирование

Pipeline сохраняет последние 200 ходов в `LOG_DIR/pipeline_*.json`.
При прерывании потока или отмене задачи сохраняется собранная часть
с кодом `interrupted` или `cancelled`.

- В начале лога идут время, ID хода, исходные чат и пользователь, общий
  тайминг, лимит итераций и итоговый код ошибки.
- `system_prompt` содержит полный системный промпт первого запроса.
  `llm_messages` содержит остальные сообщения в том порядке, в котором
  Pipeline передал их клиенту LLM. Observatory сразу показывает последние
  пять сообщений. Более ранний контекст раскрывается по запросу.
- `trigger` отдельно сохраняет тип и текст события. Для входящего хода
  это весь батч, из которого сформирован запрос. Тип `notification`
  используется, если Pipeline сформировал уведомление для модели.
  У проактивного хода в этом поле текст проактивного задания.
- `llm_iterations` идёт в порядке вызовов. У каждой итерации видны модель,
  состояние, активный чат, настройки генерации, доступные инструменты
  и длительность запроса вместе с повторами. При наличии данных от
  провайдера видны ID запроса и ответа, токены и причины повтора. Если
  провайдер отклонил нативное аудио, у следующей попытки стоит
  `audio_stripped: true`.
- Со второй итерации `context_delta` показывает, сколько сообщений убрали
  с конца предыдущего контекста и какие сообщения добавили после сохранённой
  части. Сюда попадают напоминания протокола, черновики модели, уведомления
  и результаты инструментов в формулировке, которую получила модель.
  После `enter_dialog` системное сообщение `Presence switched` с событием
  и причиной перехода видно в `context_delta` следующего запроса. При смене
  диалога также видна замена истории. Если изменился системный промпт,
  `system_prompt_diff` показывает построчные изменения.
- `response` содержит текст ответа, причину завершения, reasoning при его
  наличии и вызовы инструментов с исходными аргументами. Запрос, завершившийся
  ошибкой до получения ответа, тоже виден. `action_count` связывает
  итерацию с очередными результатами в списке `actions`.
- В конце видно решение Pipeline, включая молчание, способ ответа и выбранный
  чат. Для проактивного хода блок `proactive` также содержит решение
  State Agent и результат фактической доставки. Для входящего хода доставка
  проверяется по логам отправки.
- `write_diary` и `update_diary` записывают в `actions` результат локальной
  операции. Фоновая реорганизация пишет свои результаты в лог бота.

У фото и аудио сохраняются текстовые метки вместо тела вложения. В диагностике
провайдера сохраняются статусы, ID и тайминги. Тело ошибки провайдера и параметры
авторизации в эти данные не входят.

Просмотр доступен на странице Pipeline в Observatory и через
`GET /api/pipeline/logs`, `GET /api/pipeline/logs/{file}` и
`GET /api/pipeline/chats`. В старых файлах сохранились только промпт
последней итерации, ответы и результаты инструментов. Они открываются
с пометкой о старом формате.
Детальный API сохраняет поле `raw_llm_responses` для прежних клиентов.

## Важные константы

| Константа | Значение | Где | Описание |
|-----------|----------|-----|----------|
| `MAX_THINK_ITERATIONS` | 7 | `core/pipeline.py` | Fallback-лимит, runtime может переопределить |
| `MAX_HISTORY_IMAGES` | 3 | `core/media.py` | Фото, остающиеся нативными в истории |
| `MAX_HISTORY_AUDIOS` | 2 | `core/media.py` | Аудио, остающиеся нативными в истории |
| `JOURNAL_MAX_LINES` | 60 | `core/action_journal.py` | Сколько строк журнала попадает в промпт |
| `SEND_TEXT_LIMIT` | 200 | `core/action_journal.py` | Максимум текста `send_message` в журнале |
| `CONTEXT_MAX_TOKENS` | 30000 | `config.py` | Лимит токенов сообщений в буфере |
| `MAX_CONTEXT_TOKENS` | 10000 | `config.py` | Целевой лимит выборки контекста |
| `MAIN_LLM_MAX_TOKENS` | 2048 | `config.py` | Дефолт; пайплайн явно просит 2048 |
